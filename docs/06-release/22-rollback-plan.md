## 回滚目标与准备

回滚恢复到已知安全的代码/策略/模型/Schema组合。候选版本发布前保存previous-known-good manifest、SQLite一致性备份、配置与签名密钥管理记录；验证备份可读/恢复。当前没有产品镜像/数据库，以下为待实现流程，尚未演练。

| 情形 | 回滚策略 |
|---|---|
| 仅策略导致误拦 | 验证旧策略满足当前硬不变量并与Schema兼容后恢复旧hash；撤销旧审批 |
| 代码/模型回归 | 切回固定镜像/模型digest，配置与adapter版本配套，复验安全Gate |
| Schema前向不兼容 | 停写、导出新增审计、使用已演练迁移或恢复一致性备份；不能让旧程序直接写新库 |
| 已产生外部副作用 | 回滚软件不撤销已外发/已push/已执行；先按事件响应调查和补救 |

## 操作顺序

1. 冻结受影响高危动作，记录时间/操作者/版本和原因；停止新审批。
2. 区分尚未执行、正在执行、结果未知的动作；非幂等结果未知先与模拟/实际执行器对账，避免重放。
3. 保存当前脱敏审计增量与一致性备份。备份不能只有拷贝正在写的SQLite主文件而遗漏WAL；使用验证过的备份机制。
4. 校验目标manifest、策略安全不变量和Schema兼容性；恢复匹配版本。数据库恢复若丢失增量须明确RPO与补录流程。
5. 所有未消费旧审批令牌失效；不会通过数据库回滚复活已消费nonce。用独立持久消费日志/版本epoch保证，实施方式B在W2冻结。
6. 运行TC-13/16/18/23/26/28与TC-41，检查副作用、审计、身份和回滚结果。
7. A/B/C确认后恢复有限受控流量，观察SLO和效用，更新Dev Log/Release Notes。

## 目标与演练

赛事环境建议RTO≤30分钟；配置/策略目标RPO=0，审计恢复RPO由备份间隔和增量保留决定，首周确定，当前不承诺零丢失。W7至少演练一次策略回退和一次数据库/版本恢复，记录实际耗时、丢失事件数与审批失效结果。

禁止为恢复可用性改成高危fail-open；已知存在旁路的旧版不是合法回滚目标。需要数据不可逆迁移时必须先有roll-forward修复方案，不能靠“再装旧版本”回退。
